如果只是存储连续重复值,那这种问题也实在太没有技术含量了,所以,结合我前以前干的一件事,我打算现身说法给同志们唠叨唠叨.
服务的甲方爸爸的主要任务就是做信号采集的,其数据传输使用移动蜂窝网络,一个采集设备有6路ADC,每一路的采样精度为32位,主要采集的是一些机械振动类的信号,平均下来每一个采集设备,一天大概能产生2个GB的原始数据.
如果只是2个G是不是感觉还好,但是这个采集每次都要采集半个月,大约四五十个设备同时开始采集,而且甲方爸爸还得服务很多的甲方爷爷,也就是说一天采他1个T的数据太正常不过了.
生意做大以后,有点顶不住了,网络带宽和存储都不便宜,并且移动网络的耗电量也是整个设备的重头之重头,并且网络情况不好的时候,数据也发不出去,网络通讯带宽根本满足不了采集的带宽
当我接手擦屁股的时候,这个数据仍然是以原始数据发送的,综合讨论以后,给出了对原始数据进行压缩的方案,那么给你做,你会怎么干?
### **_段位一:LZW及其衍生算法_**
对付这类重复值比较多的数据,其实算法也挺多,首先这种采集的信号很可能大部分时间是没有意义的信号,几乎都是一大堆0,那么使用LZW和其类似的LZ77,应该能取得不错的效果.比如LZ77是怎么工作的呢?非常简单,主要分成2步
1.存储其在前面那个位置开始 2.存储其重复的长度
之后就可以还原出之后的数据了,举个栗子,例如下面的序列:
[1,2,3,a,b,c,a,b,c,a,b]
我们从左往右边扫描,直到这个位置:
[1,2,3,a,b,c | a,b,c,a,b ]
我们发现,分割符|右边的a,b,c和左边的重复了,因此上面序列可以等价为
[1,2,3,a,b,c | (重复长度为3,位置在前3个字母),a,b ]
其中,"重复长度"顾名思义
而"位置在前3个字母"是描述位置的信息,综合上述,我们其实可以更进一步,如果我们定义(重复长度是5,位置在前3个字母)如何
显然的,因为a,b,c,a,b后面的两个独立的a,b仍然在a,b,c,a,b,c,a....的循环嵌套内,因此长度比距离大,这种描述仍然能够正确工作,因此,我们可以把上面的序列编码为下面的表达方式
[1,2,3,a,b,c,(5,3)];
**_作为一种通用类算法,这个其实也非常适合解决题目中的问题.如果仅仅采用这种算法,估算平均压缩率可以做到90%左右,也就是节约了10%的带宽_**
###  _段位二_**:范式huffman压缩**
作为经典的通用压缩编码算法,怎么可能少的了经典的huffman编码,啥是huffman树再写一遍就真没意思了,哪怕非CS的专业只要有搓过代码,多多少少都有所耳闻,本身huffman树的构造也并不复杂,在网上应该很容易找到相关的资料，那么范式huffman呢，我们举一个简单的例子，例如我们对序列
a,b,c,c,c,d,d,d,d,d,d
进行编码,首先我们计算每个值出现的频率  
| symbol  | freq  |  
| --- | --- |  
| a  | 1  |  
| b  | 1  |  
| c  | 3  |  
| d  |   |  
依据这个频率,我们建立一个典型的Huffman树
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='488'%20height='483'></svg>)Huffman树
如果我们将左边以0编码,右边以1进行编码,那么,每个字母(Symbol)都可以编码为一个"Code" ,那么,huffman树可以构造成一个类似下表的结构:  
| symbol  | code  | bit(s) length  |  
| --- | --- | --- |  
| a  | 000  | 3  |  
| b  | 001  | 3  |  
| c  | 01  | 2  |  
| d  | 1  | 1  |  
因此,如果是常规的huffman树,我们需要保存huffman树每个symbol对应的code,和code对应的位长度(bits length),范式huffman本质是确定了code的一个结构,就是把code的内容规范化,比如上面这个huffman树,a是000,b是001,那么如果换成a是001,b是000,这样重新构造的huffman树也是完全成立的,但范式huffman树说不行,a可以通过它的bits length计算出来,它的值一定是确定的,那么我们就可以通过只保存bits length来重建huffman树,省了不少空间  
| 常规huffman树  | 范式huffman树  |  
| --- | --- |  
| 需要保存code和bits length  | 只需要bit length就行了,因为code可以通过bit length计算出来  |  
那么,剩下的问题就是如何通过bit length来还原code了,你可以通过查阅RFC1951但我还是想举个例子重新计算一遍:
1.首先,我们保存了a,b,c,d的位长(bits length),它们分别是(3,3,2,1) 2.然后,我们计算位长出现的频率,比如位长3出现2次,2和1只出现1次,我们根据这个构造下表
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='725'%20height='201'></svg>)
然后我们需要构造next_code,next_code构造如下代码(MAX_BITS为最大位长,比如这里是3)

```
code = 0;
bl_count[0] = 0;
for (bits = 1; bits <= MAX_BITS; bits++) 
{
    code = (code + bl_count[bits-1]) << 1;
    next_code[bits] = code;
}
```

这样我们就可以构造出next_code了
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='728'%20height='192'></svg>)
最后,我们依据位长出现频率构造出code(其实就是next_code根据频次累加),代码如下

```
for (n = 0;  n <= max_code; n++) 
{
    len = tree[n].Len;
    if (len != 0) {
    Code[n] = next_code[len];
    next_code[len]++;
    }
}
```

  
  
| symbol  | 位长(bits length)  | code  | code的二进制  |  
| --- | --- | --- | --- |  
| a  | 3  | 6  | (110)  |  
| b  | 3  | 6+1=7  | (111)  |  
| c  | 2  | 2  | (10)  |  
| d  | 1  | 0  | (0)  |  
于是,我们的范式huffman树,仅仅需要保存bit length就能够还原了,大大节省了存储空间,结合LZ77 _采用这种两法,估算平均压缩率可以做到72%左右,也就是节约了28%的带宽._
###  _段位三_**:改变数据的组织格式**
相信绝大多数的"调包侠"压缩率做到72%几乎就是极限了,因为LZ77+huffman就是经典的deflate压缩算法,这也是zip,gzip所采用的经典算法,如果你熟悉LZ77的算法,把LZ77的前向搜索范围拉满,压缩率也就是72%.并且其附带着大量的运算消耗.
通用压缩算法,到这里再要有质的提升很难了,哪怕你换用7z,也就是把压缩率从72%提升到了68%
解下来怎么办呢?
观察发送数据包的阻止格式,我发现了猫腻,因为数据包格式是以这样进行组织的
{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}{包头,时间,第一个通道AD采样数据,第二个通道AD采样数据,第三个通道AD采样的数据.......}
也就说,每个数据包就只是存储了某个瞬间采集的数据,导致前后数据的关联性极差,其导致了LZ77的性能下降,更是导致原本关联性强的连续数据变得离散无序了
怎么办呢.改变数据的存储方式,一个数据包应该是这样
{包头,时间1,时间2,时间3...第一个通道AD采样数据1,数据2,数据3....第二个通道AD采样数据1,数据2,数据3....}
将所有前后有关联的数据组织在一起,你可能问了这有啥用?
注意了,位置信息也是很重要的一维信息,而LZW正是强位置排列相关的,不同的数据排列方式,其压缩效果天差地别.例如这里的采样深度是32位,因为前16位甚至是24位在没有关键信号来的时候很可能是不变的,后面8位是传感器的精度噪声,因此,组织排列方式后,能够大大提高lzw的性能.
**_改变数字组织方式了.再压,这个时候,压缩率干到了48%_**
###  _段位四_ :差分编码
如果你再次意识到.正因为前后数据存在强关联性,如果我们把后面一个值减去前面那个会怎么样?
比如说:
{1000,1001,1003,1005}做完差分以后就是{1000,1,2,2}
{2000,2001,2003,2005}做完差分是{2000,1,2,2}
这两段数据原本是不相关的,做完以后居然出现了3个相同的数据,压缩率岂不是进一步优化了,
**_仅仅多做一个差,.再压,这个时候,压缩率干到了36%_**
**_段位五:线性预测编码_**
注意到时间戳绝大部分时候是线性增长的,但因为客户需求,采集的晶振时钟可能存在偏差需要修正,因此无法保证所有的时间都是线性增加的,不然也不用加这个字段了
例如一段时间信号分别是
1001 1003 1005 1007 1008 1011
如果只是做差分,那么
{1001 2 2 2 1 3}
如果,我们不仅仅是简单的做差分,而是用一个线性预测序列和这个时间序列信号做差分
{1001 1003 1005 1007 1009 1011}
那么结果就是
{0 0 0 0 -1 0}
是不是比差分信号好多了
**_对时间信号做线性预测编码后,压缩率干到了28%,几乎把时间那点扰动的数据压没了_**
  

**_段位六:频域压缩编码_**
尽管采样率是32位深度的,其低位数据几乎都是无序的精度噪声干扰,故通过对频域的分析,其展示为全频段的能量均匀分布.但是正是这部分的数据,也是占据了大部分的编码空间的罪魁祸首
但是这段信号你还不能直接丢,毕竟32位采样深度,听上去也比24位更加的高大上,就像hifi,虽然24b和16b在听觉上已经非常人能够分辨,但24b的就是更HIFI,怎么办?
好办,对这部分幸好进行低通滤波.第一可以采用简单的均值滤波办法,越低通压缩效果越好
保守点,鉴于其运算性能与效果考虑,构造一个n阶的均值滤波器
**_而不同阶数的滤波器滤波后,压缩率来到了12%~22%,几乎是段位五再砍了40%_**
  

**_段位七:频域编码+频域预测编码_**
_再次观察客户需求,采集的是什么,振动数据!回到我们经典的数学物理方法_
以最经典的一维弦振动方程为例:
\frac{\partial^{2}u}{\partial^{2}t}=c^2\frac{\partial^{2}u}{\partial^{2}x}
设一细弦两端被固定,长度为L,那么其微分方程应满足边值条件
u(0,t)=u(L,t)=0 (t\geq0)
u(x,t) 的通解为
u_n(x,t)={sin(\frac{(n\pi)}{L}x)}(a_ncos(\frac{n\pi c}{L})+b_nsin(\frac{n\pi c}{L}))
得到满足边值条件的完整解
u(x,t)=\sum_{n=1}^{\infty}{u_{n}(x,t)}=\sum_{n=1}^{\infty}{sin(\frac{(n\pi)}{L}x)}(a_ncos(\frac{n\pi c}{L})+b_nsin(\frac{n\pi c}{L}))
通过上式我们得知, u(x,t) 是 通项u_n(x,t) 的无穷累加和,因此,震动信号实际是以固有频率为基准的多个整数倍频率正弦振动的叠加
因此,有用的信号看起来差不多是这个样子
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='632'%20height='605'></svg>)
可以看到,信号在频域有明显的能量聚集性,也就是说,通过对于平常的时候,记录时域数据可能更加合理,但对于有效数据,采用频域对信号进行编码,会比在时域高效的多,哪怕客户有高精度的采样深度需求,使用频域+相位+差分的编码方式,也能够大大的减少编码尺寸.
**搞起,_压缩率来到了8%~16%,在原来的基础上,再次提升了了一阶_**
  

**_至此,几乎已经压缩了将近90%的空间,不用和运营商洽谈推杯换盏求来点价格优惠_**
**_也不用硬件更改加功耗,堆物料_**
**_仅靠软件层面的处理,就可以将带宽和存储的费用打了一折._**
**_这不是脑洞开发,这全是白花花的小钱钱啊_**

_q:能不能用音频编码？_
a:实际上频域预测编码的思路正是音频编码格式中的常见做法，例如flac格式其实原理上是非常类似的，但考虑到直接音频编码效率并不高，在嵌入式设备中可能运算时间过长会也会导致功耗上升甚至超过实际信号平均采样速率导致算法不可用，故需要利用一些算法手段将其优化，例如有效信号中明显的共振峰特性，可以使用倒谱域分析法快速提取关键信号，一可快速判断是否有进行频域预测编码的价值二可用于快速构造预测序列。
q:能否用aac，mp3等方式的有损压缩
a:不可，音频有损压缩多为基于人类听觉(频域掩蔽，后滞掩蔽或mfcc特性)构建的压缩模型，并非简单的低通滤波，客户采上来的信号显然不是为了“好听”。
最后除了振动还有时间，位置等其它数据，想靠直接调包一劳永逸是行不通的
