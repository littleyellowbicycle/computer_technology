如果你要绝对精确,恐怕这就是一个物理学的问题了,
所以我们现实一点,这里我们还是主要讨论一下怎么尽可能达到这个5ms,并尽可能缩小这个偏差
那么问题来了,我们到底能做到多小的偏差捏?
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='373'%20height='419'></svg>)
所以,为了试试这个"极限",我们来假设这样一个函数

```
int light;
void power_switch()
{
	light=~light;
}
```

这个函数很简单,用来模拟开灯关灯,调用一次开灯,再调用一次关灯,以此类推.所以我们要做的,就是均匀的开灯关灯.
我们先来试试题目中这个

```
px_uint t1, t2;
for (int i = 0; i < 100; i++)
{
	t1 = PX_TimeGetTimeUs();
	PX_Sleep(5);
	power_switch();
	t2 = PX_TimeGetTimeUs();
	printf("Time: %u.%u\n", (t2 - t1)/1000, (t2 - t1) % 1000);
}
```

![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='948'%20height='481'></svg>)
可以看到效果是真不咋地,原本应该延迟5ms的却延迟了10ms-15ms,偏差都比延迟还大了,偏差率达到了100-200%.
**_为什么捏,主要是Windows下Sleep函数会导致线程切换,下一次时间片轮询到就不知道是后年马月了,这和操作系统底层的线程调度机制有关。_**
## **所以第一步，干掉Sleep**
怎么做呢？比如用下面这种方式

```
px_uint lasttime=PX_TimeGetTimeUs();
for (int i = 0; i < 100; i++)
{
	while (1)
	{
		px_uint now = PX_TimeGetTimeUs();
		if (now - lasttime >= 5000)
		{
			power_switch();
			printf("Diff: %u.%u\n", (now - lasttime) / 1000, (now - lasttime) % 1000);
			lasttime = now;
			break;
		}
	}
		
}
```

![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='804'%20height='683'></svg>)
可以看到，效果好多了，我们通过不断轮询时间的方式（如果超过5ms就执行函数），在多数时候我们可以把这个时延控制在亚微秒秒级，但是在一些时候仍然出现了和sleep类似的偏差，这是为什么捏
**因为通过这种循环轮询的方式，我们仍然避免不了操作系统底层的调度机制，主线程时间片到了以后，操作系统仍然会进行切换，提高进程优先级有助于减少这种问题抖动，但是除非我们能完全抢占一个核心，或者将时间片切的很短很短，我们仍然无法完全避免这种抖动。**
## **下一步，干掉操作系统**
现在给大家介绍一个新朋友Zynq XC7Z020 Soc
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='895'%20height='667'></svg>)

![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='1234'%20height='569'></svg>)

第三,用Zynq的FPGA部分搓一个计时器,这个计时器使用AXI Lite总线进行访问,完整代码我就不贴了,你可以用Xilinx的模板,然后把写那一部分的模块直接删掉,搓成大概下面这个样子:

然后我们Export Hardware,打开Vitis创建一个Standalone的无操作系统环境
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='2087'%20height='1395'></svg>)
输入以下测试代码:

```
int light;
void power_switch()
{
	light=~light;
}

unsigned int diff_time[100];
int main()
{
    unsigned int lasttime=*(unsigned int *)0x43C00000;

	for (int i = 0; i < 100; i++)
	{
		while (1)
		{
			unsigned int now = *(unsigned int *)0x43C00000;
			if (now - lasttime >= 500000)
			{
				diff_time[i] = now - lasttime;

				lasttime = now;
				break;
			}
		}
	}

}
```

其中,7a129的十进制是500009,而我们的Clock运行在100Mhz的时钟里,500000代表5ms,多出来的9代表90ns,也就是说,我们把时延偏差已经缩短到了百纳秒级别！大概在0.002%左右，这应该是目前回答中精度最高的了。
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='643'%20height='389'></svg>)
不要惊慌，到这里都还只是基操前菜，我们还远远没有摸到极限的屁股，坐好了，让我们开始加速了。
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='1239'%20height='729'></svg>)
要想进一步提升误差精度,一个我们考虑继续提升CPU和总线的频率,以进一步降低一些指令和访存Latency对精度造成影响,但目前我们的CPU已经工作在800Mhz频率下,对于嵌入式系统而言这已经是一个比较高的频率了,并且一些访存和功耗墙和总线仲裁问题,可能回导致这个时延进一步发生抖动。
是时候干掉CPU自己搓一个了！
但是在此之前，我们仍然需要认识到C语言就是设计在CPU体系中的,所以要干掉CPU之前,我们应该先干掉编译器自己搓一个,以达到编译结果的完全"我说了算"的效果,可能有观众朋友要问了,题目中不是说C和C++么.有没有考虑一下我们C++,第一C++的抽象特性可能带来额外更难以控制的时延开销,第二C++的编译器我一个人也搓不动,所以后面我们都不再考虑了.因此:
## **下一步,干掉C编译器,自己搓**
关于怎么自己搓一个编译器,在这个回答里我并不想花太多的笔墨,如果你有兴趣,你可以看一个我远古时期写的文章,上面有描述如何实现一个从词法-语法-IR-指令流-虚拟机的编译执行系统.
[](https://zhuanlan.zhihu.com/p/72356928)
总的来说,在这个编译架构中我们分为前端和后端,前端你可以认为是将C语言编译成代码,而后端是将IR进一步优化后编译为指令流,但这里的虚拟机不再是虚拟机,我们将使用FPGA自己搓一个能直接执行指令流的CPU
当然为了简化操作,我们甚至只需要下面这个代码

```
int light;
void main()
{
	light=~light;
}
```

你可能会问了,怎么只有一个main函数,实际上这是我们专用CPU的特色,我们完全可以设计为当main函数RET后,延迟个5ms然后重新执行main函数,这样我们就能省去不少的麻烦,为了给各位展示一下这个编译系统的抛瓦,我仍然使用PainterEngine及其内部集成的调试器给各位演示编译的结果.关于怎么编译PainterEngine在官网和我文章里都有,我就直接show your code了

## **下一步，干掉CPU,自己搓!!!**
首先,寄存器我们需要IP,BP,SP,R1,
其中IP是指令位置指针,BP,SP其实在这里没啥用.当然我同样将它实现,以展示这真是一个正儿八经的CPU，虽然它未必是图灵完备的。
而内存我们只需要一个内存单元就行了,因为我们只需要GLOBAL[0]，但我仍然为CPU设计了128bytes的指令空间和堆栈内存空间，不然它就不像CPU了
而指令我们需要：
PUSH 压栈指令,需要实现BP访问的通路
MOV 赋值指令，其中它需要实现SP->BP寄存器通路及内存到R1寄存器的双向通路
POP 出栈指令,需要实现BP访问的通路
INV 取反指令,实现对R1的访问
RET 返回指令，同时设置5ms延迟
我们可以直接设计一个定长指令集,以实现上述IR到指令流的隐射关系,例如在上面的指令集中,我们指令流可以完全映射到010203040506,因为我们一共就6条指令，可以狠狠的偷懒。
接下来让我们设计一个哈佛结构的CPU，这是一个非常简易的CPU，简单到只能执行我们上面的6条指令且不是图灵完备的，它采用经典的哈佛架构，可以看到它指令存储器和内存是分离的，而CPU分别访问它们以执行指令
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='1182'%20height='517'></svg>)
那么结果如何呢，这里我们打开仿真器，查看其输出波形可以看到，函数在非常精准的按照5ms的间隔进行执行
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='1280'%20height='714'></svg>)
那么精度可以达到多少呢？以这里的寄存器翻转（灯泡亮灭）为例，因为这是固定频率的CPU（指令延迟造成的相位偏移并不影响执行间隔）因此其实际延迟取决于信号的上升沿抖动时间和晶振PPS误差，因为对应我们这个50Mhz晶振其ppm误差大约在十几，**所以晶振偏差大约在每秒0.00001%之间，而换算到5ms之间的偏差，则在每次500皮秒左右，如果愿意花钱使用更高精度的恒温晶振(大约误差在百兆0.1ppm),则可以将误差控制在5皮秒**
**到此,我们成功将误差压缩到了皮秒级别**
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='941'%20height='604'></svg>)
给出该CPU代码：

```
`timescale 1ns / 1ns

`define PX_CPU_STATE_SLEEP 8'h00
`define PX_CPU_STATE_IP 8'h01
`define PX_CPU_STATE_FETCH 8'h02
`define PX_CPU_STATE_FETCH_PULL 8'h03
`define PX_CPU_STATE_DECODE 8'h04
`define PX_CPU_STATE_READ 8'h05
`define PX_CPU_STATE_READ_PULL 8'h06
`define PX_CPU_STATE_WRITE 8'h07
`define PX_CPU_STATE_END 8'h08
`define PX_CPU_STATE_ERR 8'h09

`define PX_INSTR_PUSH_BP 8'h00
`define PX_INSTR_MOV_BP_SP 8'h01
`define PX_INSTR_MOV_R1_G0 8'h02
`define PX_INSTR_INV_R1 8'h03
`define PX_INSTR_MOV_G0_R1 8'h04
`define PX_INSTR_POP_BP 8'h05
`define PX_INSTR_RET 8'h06


module microCPU(
    input wire        i_wire_clk,
    input wire        i_wire_resetn,

    output wire [7:0] o_wire_instr_ip,
    output wire       o_wire_instr_ena,
    input wire [7:0]  i_wire_instr_data,
    
    output wire [7:0] o_wire_memory_addr,
    output wire       o_memory_ena,
    input wire [7:0]  i_wire_memory_data,

    output wire        o_memory_enw,
    output wire [7:0]  o_wire_memory_data
    );
    reg [7:0] reg_r1;
    reg [7:0] reg_ip;
    reg [7:0] reg_sp;
    reg [7:0] reg_bp;
    reg [7:0] reg_cpu_state;
    reg [19:0] reg_sleep;

    reg [7:0] reg_memory_addr;
    reg [7:0] reg_memory_data;
    reg [7:0] reg_instr_data;
    reg [7:0] reg_instr_ip;
    reg reg_instr_en;
    reg reg_memory_ena;
    reg reg_memory_enw;

    assign o_wire_instr_ip = reg_instr_ip;
    assign o_wire_instr_ena = reg_instr_en;
    assign o_wire_memory_addr = reg_memory_addr;
    assign o_memory_ena = reg_memory_ena;
    assign o_wire_memory_data = reg_memory_data;
    assign o_memory_enw = reg_memory_enw;

    always @(posedge i_wire_clk or negedge i_wire_resetn) 
    begin
        if (!i_wire_resetn) begin
            reg_r1 <= 8'h00;
            reg_ip <= 8'h01;
            reg_sp <= 8'hff;
            reg_bp <= 8'h00;
            reg_cpu_state <= `PX_CPU_STATE_SLEEP;
            reg_sleep <= 20'h00;
            reg_memory_ena<= 1'b0;
            reg_memory_enw<= 1'b0;
            reg_instr_ip <= 8'h00;
            reg_instr_en <= 1'b0;
            reg_memory_addr <= 8'h00;
            reg_memory_data <= 8'h00;
            reg_instr_data <= 8'h00;
        end 
        else 
        begin
            case(reg_cpu_state)
            `PX_CPU_STATE_SLEEP:
                begin
                    if (reg_sleep == 20'h0) begin
                        reg_cpu_state <= `PX_CPU_STATE_IP;
                    end
                    else begin
                        reg_sleep <= reg_sleep - 20'h01;
                    end
                end
            `PX_CPU_STATE_IP:
                begin
                    reg_instr_ip <= reg_ip;
                    reg_instr_en <= 1'b1;
                    reg_memory_ena <= 1'b1;
                    reg_memory_enw <= 1'b0;
                    reg_ip <= reg_ip + 8'h01;
                    reg_cpu_state <= `PX_CPU_STATE_FETCH;
                end
            `PX_CPU_STATE_FETCH:
                begin
                    reg_instr_en <= 1'b0;
                    reg_memory_ena <= 1'b0;
                    reg_memory_enw <= 1'b0;
                    reg_cpu_state <= `PX_CPU_STATE_FETCH_PULL;
                end
            `PX_CPU_STATE_FETCH_PULL:
                begin
                    reg_instr_data <= i_wire_instr_data;
                    reg_cpu_state <= `PX_CPU_STATE_DECODE;
                end
            `PX_CPU_STATE_DECODE:
                begin
                    case (reg_instr_data)
                    `PX_INSTR_PUSH_BP:
                        begin
                            reg_memory_addr <= reg_sp;
                            reg_memory_data <= reg_bp;
                            reg_memory_enw <= 1'b1;
                            reg_sp <= reg_sp - 8'h01;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    `PX_INSTR_MOV_BP_SP:
                        begin
                            reg_bp <= reg_sp;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    `PX_INSTR_MOV_R1_G0:
                        begin
                            reg_memory_addr <= 0;
                            reg_memory_ena <= 1'b1;
                            reg_cpu_state <= `PX_CPU_STATE_READ;
                        end
                    `PX_INSTR_INV_R1:
                        begin
                            reg_r1 <= ~reg_r1;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    `PX_INSTR_MOV_G0_R1:
                        begin
                            reg_memory_addr <= 0;
                            reg_memory_data <= reg_r1;
                            reg_memory_enw <= 1'b1;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    `PX_INSTR_POP_BP:
                        begin
                            reg_memory_addr <= reg_sp;
                            reg_memory_ena <= 1'b1;
                            reg_sp <= reg_sp + 8'h01;
                            reg_cpu_state <= `PX_CPU_STATE_READ;
                        end
                    `PX_INSTR_RET:
                        begin
                            reg_sleep <= 32'd500000;
                            reg_ip <= 8'd1;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    default:
                        begin
                            reg_cpu_state <= `PX_CPU_STATE_ERR;
                        end
                    endcase
                end
            `PX_CPU_STATE_READ:
                begin
                    reg_cpu_state <= `PX_CPU_STATE_READ_PULL;
                end
            `PX_CPU_STATE_READ_PULL:
                begin
                    case (reg_instr_data)
                    `PX_INSTR_MOV_R1_G0:
                        begin
                            reg_r1 <= i_wire_memory_data;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    `PX_INSTR_POP_BP:
                        begin
                            reg_bp <= i_wire_memory_data;
                            reg_cpu_state <= `PX_CPU_STATE_END;
                        end
                    default:
                        begin
                            reg_cpu_state <= `PX_CPU_STATE_ERR;
                        end
                    endcase
                end
            `PX_CPU_STATE_END:
                begin
                    reg_memory_enw <= 1'b0;
                    reg_memory_ena <= 1'b0;
                    reg_cpu_state <= `PX_CPU_STATE_SLEEP;
                end
            endcase
        end
    end

endmodule

```

所以,让我们进一步消除晶振ppm,真正把这个精度干到皮秒级
那么原理上怎么做呢？经过了一系列短暂的思考后，方案其实很简单，我先用低速时钟举个栗子,比如我们需要一个非常准确的100HZ的时钟，我们先通过mmcm或者pll,把一个时钟源放大到1000HZ,之所以要做这个倍频率操作,是为了给我们的训钟模块提供对输出时钟更高的精度控制,然后就是构造我们的输出时钟了,因为我们需要的是100Hz的时钟,因此,输出时钟和输入时钟的脉冲比是1:10,也就是说上面的十个脉冲,下面我们输出一个脉冲,这可以由verilog一个简单的counter来完成计数(比如1:10就是输出在输入的每5个脉冲进行电平翻转一次)
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='601'%20height='455'></svg>)
但是,因为晶振的ppm误差,显然这个1000HZ不可能是完全准确的1000HZ,在pps信号到来时,它可能是1008hz,那么这个多出来的时钟,我们需要在下一秒对其进行修正,比如,原本输出一个脉冲是1:10的关系,如果我们将他修改为1:9,就可以把前面多出来的一个时钟的"账单给平了"
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='596'%20height='338'></svg>)
那么,我们就可以通过调整输出脉冲的宽度,让输出时钟在补齐前一次pps时间段的晶振误差,仅仅需要付出<10%的脉冲宽度误差,在高速时钟比如100M输入时钟时,这个误差仅仅只有10ns,可以说,如果100M时钟的误差在50ppm,输出时钟是10M,那么,这500ns的误差会被分散到1秒的样本中,5ms的误差大约会在500/200=2~3ps级别!
那么,实现时会碰到什么问题呢?
首先我们碰到的第一个问题,是如何去做输入时钟的counter,因为GPS的PPS信号和FPGA的输入信号,并不是一个同步的时钟源,因此PPS和输入时钟在实际上板是几乎是不可能对齐的
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='818'%20height='272'></svg>)
因此,如果我们真的用"当PPS信号到来的时候去数前一秒的脉冲数",很可能在极端情况下面临非常棘手的亚稳态问题,因此,聪明点的做法应该是,因为pps信号基本都有几十到几百微秒甚至毫秒级别的保持时间,因此,我们仅在pps信号到来后的第一个输入时钟去计算上一秒的实际脉冲数量,这样就避免了异步时钟可能带来的亚稳态问题.而这个最多十纳秒的延迟,却几乎可以忽略不计,为了完成这一步,我们需要额外添加一个delay0信号,这个信号在pps信号在pps信号到来后拉高,那么我们就可以通过判断"delay0是低电平而pps是高电平"来区分"pps信号到来后的第一个时钟了"
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='905'%20height='180'></svg>)
pps信号可能是不稳定的,如何保证系统对pps信号干扰的抵抗,提高系统鲁棒性又是另一个问题,比如你当我们发现pps信号并没有像预期之中到来时,我们可以沿用上一次的counter对下一秒的脉冲进行补偿,这样只要不是"几分钟"内,pps信号毛都见不到,我们的"训钟"模块输出的信号质量就是满足要求的,因此在verilog中我额外加入了reg stable,来判断当前的补偿到底是从之前的算取还是按上一次取,当然只有在pps信号稳定8秒后,系统才进入stable状态,只要pps有一次丢失就会退出,但系统不一定需要总是工作在stable状态,才能输出符合要求的信号.
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='647'%20height='131'></svg>)
同时,如何进行插值也是一个大问题,例如,你不能让输出信号的前100个脉冲来承担误差的一切,ppm偏差应该尽可能的分散在下一秒的所有脉冲中(但不能完全均分,因为你需要部分脉冲给ppm误差预留一段补偿空间),比如说后一秒的100个脉冲,我们用前面90个去补齐这一秒多出来的或更少的时钟误差,而后面10个给出预留量,因此这个训钟模块的一些参数可能需要通过实验去获得,我这里预留了一个gap参数,表示每隔几个输出时钟进行一次补偿,以实现这种误差均摊
![](data:image/svg+xml;utf8,<svg%20xmlns='http://www.w3.org/2000/svg'%20width='744'%20height='265'></svg>)
当然,还有比如输入时钟和输出时钟频率非整数倍频,如果出现1:5这种情况,高电平保持时间是3个还是2个之类的边边角角的细节问题,在文中就不一一阐述了.
但总的来说,这个训钟模块的工作时间越久,平均误差会越小并趋于收敛,同时它也没有工作久以后误差累积的问题.
但这个精度的脉冲,在CPU控制系统的任意一个波动都远大于时钟的精度误差.因此继续修正物理时钟已经意义不大了,需要在CPU架构方面进一步做对应设计才能达到.
