# 一台主机TCP连接数量的真实限制

## 核心结论
> TCP连接由 [[socket 四元组]]（源IP、源端口、目标IP、目标端口）唯一标识，因此单台主机的连接上限远不止 65535。真正的瓶颈来自临时端口号、文件描述符、线程/IO模型、内存与 CPU 五个维度的资源约束，每一项都可调优，但终归受物理硬件限制。

## 详细内容
## 核心结论

TCP连接由 [[socket 四元组]]（源IP、源端口、目标IP、目标端口）唯一标识，因此单台主机的连接上限远不止 65535。真正的瓶颈来自临时端口号、文件描述符、线程/IO模型、内存与 CPU 五个维度的资源约束，每一项都可调优，但终归受物理硬件限制。

## 为什么不是 65535

TCP连接的两端通过四元组绑定：`源IP:源端口 <-> 目标IP:目标端口`。只要四元组不重复，理论上就能不断建立新连接。"最多 65535 个连接"的说法源自 [[端口号]] 是 16 位的误解，但它忽略了目标端 IP 和端口可以任意组合的事实。

## 五个维度的限制

### 1. 临时端口号

客户端每建立一个连接都需要占用一个源端口。Linux 默认通过 `ip_local_port_range`（典型值 `1024~65000`）限制可用范围，仅约 63977 个。

修改方式：
```
net.ipv4.ip_local_port_range = 1024 65000
```

突破手段：变换目标 IP 或目标端口，让四元组保持唯一即可绕过端口号耗尽。

### 2. 文件描述符

Linux 下 socket 也是文件，每个连接占用一个 [[文件描述符]]。系统从三个层面限制：

- **系统级**：`/proc/sys/fs/file-max`
- **用户级**：`/etc/security/limits.conf`
- **进程级**：`/proc/sys/fs/nr_open`

耗尽时报错 `too many open files`，可通过 `ulimit -n` 或写入 `/proc/sys/fs/nr_open` 调大。

### 3. 线程与 IO 模型

传统"一连接一线程"模型在连接数过万时即遭遇 [[C10K]] 问题——线程上下文切换开销拖垮系统。解决方案是 [[IO 多路复用]]（select/poll/epoll），用少量线程管理海量连接，这也是现代高并发服务器的基础。

### 4. 内存

每个 socket 对象及其收发缓冲区都要占用内存。缓冲区大小由 `net.ipv4.tcp_wmem`、`tcp_rmem` 等参数决定。内存耗尽时触发 [[OOM]]，操作系统开始杀进程。

### 5. CPU

CPU 占用率持续 100% 时，系统响应迟滞直至失去可用性，最终被强制重启。CPU 是最难"调大"的资源，只能靠减少单连接计算量或横向扩展解决。

## 资源-限制速查表

| 资源 | 系统配置项 | 单连接占用 | 耗尽现象 |
|------|-----------|-----------|---------|
| 临时端口号 | `ip_local_port_range` | 1 | cannot assign requested address |
| 文件描述符 | `fs.file-max` / `ulimit -n` | 1 | too many open files |
| 进程/线程数 | ulimit / 线程模型 | 取决于 IO 模型 | 系统崩溃 |
| 内存 | 物理内存 + 缓冲区参数 | 取决于缓冲区大小 | OOM |
| CPU | 硬件决定 | 取决于业务逻辑 | 卡死 |

## 实践建议

1. 高并发服务优先采用 [[IO 多路复用]] 替代线程模型；
2. 调大 `file-max`、`nr_open`、`ulimit` 解除文件描述符限制；
3. 根据业务峰值评估端口号范围，必要时扩大 `ip_local_port_range`；
4. 监控内存与 CPU 使用率，预留安全余量。
