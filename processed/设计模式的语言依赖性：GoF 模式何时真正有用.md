# 设计模式的语言依赖性：GoF 模式何时真正有用

## 核心结论
> GoF 提出的 23 个面向对象[[设计模式]]在很大程度上是静态[[面向对象编程]]语言的特性补丁；在拥有一等函数、一等类型、反射或多分派机制的现代语言中，绝大多数模式要么被语言原生特性直接取代，要么变得多余。正确学习设计模式的方式不是整体地学习设计模式，而是具体到每一个模式，判断它在你所用语言中是否仍有独立价值。

## 详细内容
## 背景

陈硕在知乎对如何正确地使用[[设计模式]]这一问题给出的回答核心是：**除非你还在写 Java，否则 GoF 设计模式真没多大用处**。这一观点与 Peter Norvig 早在 1996 年发表的著名论文 *Design Patterns in Dynamic Languages*（参见 [Norvig 原文 PDF](http://norvig.com/design-patterns/design-patterns.pdf)）一脉相承。

## 关键判断维度

GoF 在《Design Patterns》中列举的 23 个面向对象模式之所以在 1990 年代有教学价值，是因为当时的 C++/Java 缺乏几个关键的现代语言能力。可以从以下三条线索判断一个模式在你所用语言中是否仍然必要：

1. **类型能否像变量一样赋值并传递**——一旦可以，很多[[创建型模式]]（如 [[Factory Method]]、[[Abstract Factory]]）就没用了。
2. **函数能否像变量一样赋值并传递**——一旦可以，很多[[行为型模式]]（如 [[Command]]、[[Strategy]]）就没用了。
3. **语言风格是否反对叠床架屋的 class hierarchy**——一旦反对，很多[[结构型模式]]（如 [[Adapter]]、[[Decorator]] 的部分动机）就不再必要。

## 几个具体的例子

- **[[Observer 模式]]**：C# 内置 [[delegate]] / event，Java 8 之后有 Lambda，该模式被原生机制取代。
- **[[Prototype 模式]]**：Python 中 `type(x)` 能拿到运行时类型，再用该类型构造对象即可，等价于原型克隆。
- **[[Factory Method 模式]]**：只要类型能作为参数传递，`getCreator(SomeClass)` 就能直接返回构造器，模式化为一个高阶函数。
- **[[Command]] / [[Strategy]]**：函数是一等公民后，模式本质退化为把函数存进变量或作为参数传递。
- **[[Singleton 模式]]**：最简单的、也最被滥用的模式；有[[模块系统]]或全局变量的语言（如 Python module、Go package-level var）几乎完全用不到它。
- **[[Visitor 模式]]**：本来就没多大用；支持 [[multiple dispatch]] 的语言（如 Julia、Clojure）则完全不需要。

## 学习建议

不要泛泛地学习设计模式，而要具体到每一个模式：

1. 弄清这个模式当年是**弥补了语言的哪项缺失**；
2. 检查你所用语言的**现代特性**（一等函数、泛型、反射、模式匹配、ADT、宏等）是否已经填补了该缺失；
3. 如果已被语言原生支持，则该模式在你的语境下**不再具备独立的教学或设计价值**；若仍有部分动机未被覆盖，再考虑是否值得引入该模式。

把模式当成一个总体去崇拜或反对都是错误的做法：模式**作为语言缺陷的化石标本**有其历史价值，但作为**当前工程实践的指导模板**则需要严格的语境校验。
